Our side: `packages/protocol/src/{frame,read,write,blocks,reply}.ts` at HEAD `35d4609` plus the staged (not committed) `blocks.ts`, `index.ts` edits from another session (stage decoders). The files read are the working tree; blob prefixes (`git hash-object`) at read time: `blocks.ts` 197b75be, `frame.ts` d567c89f, `read.ts` 31042fca, `reply.ts` dbfe5322, `write.ts` 99a40884.

Driver side: serializer `0x4ba180`..`0x4bac19` (config + display blocks), transaction `0x4840e0`, wrappers `0x488140` (`0x06`), `0x4888d0` (`0x05`), `0x488640` (`0x35`), `0x488b60` (`0x1a`), `0x488d50` (`0xaa`). Evidence chains are in `docs/settings/config-block.md`; this file does not repeat them.

Method (`~/.cache/beastx-validate/validate.ts`, output `run-output.txt`, `bun` run from `packages/protocol`):
1. "Driver bytes" are either a **capture** (the 10 golden packets of `refs/wlmouse-beastx/README.md`, quoted in `docs/PROTOCOL.md`) or a **driver model**: the script builds the frame from the offsets and the frame rule in the docs with its own CRC-16/MODBUS (not imported from our code), then compares byte for byte with our builder output (64 B).
2. Tag **fact** = capture, or code address with both sides' bytes equal. Tag **inference** = driver bytes come from the model only (never seen on the wire).
3. Base block for the model rows: captured `block[0..23]` (polling 3, LOD 0), `block[86..92]` = `1e 00 58 02 0a 01 01`, rest zero. Frames shown are bytes 0..31 (bytes 32..63 are zero everywhere).

## Divergences (fix list)

| # | Setting | Evidence | Suggested fix |
|---|---|---|---|
| D-1 | Polling 2000/4000 Hz vs High Mode | Driver `0x463027`..`0x463048` (`config-block.md` s4): selecting polling idx > 3 while High Mode (`block[10]`) is on **turns High Mode off**, so the sent block has `block[10]=0`. Ours (`writeConfigPatch`, `applySettingsPatch`) never touches `block[10]`. Script, base with `block[10]=1`, polling 5: ours `04 7f c6 06 18 .. 95 01 01 05 ..`, driver model `04 7f 07 06 18 .. 95 01 00 05 ..` (the driver model equals the golden "Poll 4000Hz" frame, CRC `0x077f`; ours differs in `block[10]` and CRC `c6`). | In `writeConfigPatch`, when `pollingIndex > 3`, also set `block[10]=0` (add a `HIGH_MODE = 10` constant). The mirror rule (High Mode on while polling > 3 sets polling to 3, `0x463a91`..`0x463ab5`) only matters if we add a High Mode setter. |
| D-2 | Sleep value domain | Driver only emits 30/60/300 s (`0x4ba31c`..`0x4ba36e`, UI idx 1..3 `0x4c17d0`; idx 0 leaves the old bytes). Ours accepts any u16 (`SETTING_LIMITS.sleepSeconds = 0xffff`); `sleepSeconds: 45` gives `2d 00`, a value the vendor never sends and the vendor parser maps back to nothing (it reads only the low byte, `0x4b72a7`..`0x4b7333`, matching `0x1e/0x3c/0x2c` only). | Restrict the writer to `{30, 60, 300}` (or encode as enum idx 1..3) until the device range is known. |
| D-3 | Debounce value domain | Driver UI list is 0..12 ms (`mousedevice.xml:497`, hidden control); default 10. Ours accepts 0..255. The stock UI never exposes it, so this is a gap, not a byte mismatch. | Limit to 0..12 until the device range is known. |
| D-4 | Write sequence | Driver always sends `0xaa`, `0x01`, then **all five** `0x06` chunks, then `0x36` (13 B), then `0x02` (`0x4ba9a0`..`0x4bab7f`, `PROTOCOL.md` write path). Ours emits only the chunks whose bytes changed and no `0xaa`/`0x01`/`0x02` (frames list only). The only external capture (third-party) is a bare single `0x06` chunk 0, so a bare chunk is not refuted. | Caller decision (not a byte fix): either wrap writes in `0xaa`,`0x01`..`0x02` or stay on the capture shape. Persistence (does the device keep a write without `0x02`) is unknown; verify on device before a persistence claim. |
| D-5 | Bytes the driver sets itself, we echo | The driver overwrites `block[0]` (profile arg), `block[88..89]=58 02`, `block[93..96]`, `[97..98]`, `[104]`, the clock `[107..112]` and `disp[0..5]` copies (`config-block.md` s1/s2). Ours writes back what was read (read-modify-write). Equal only if the device already holds those values. Not provable without a device read. | None for byte parity; just do not claim parity for these bytes. Clock: if the device needs a fresh time, that is a separate feature (out of scope here). |
| D-6 | Stage count / DPI stage write | No builder or decoder exists in our code for `block[9]` (count) or for writing stages. `decodeStages` reads only. | Add them if the UI needs them; see rows below. |

## Notes for reviewers

- Hex abbreviation: where a cell shows `..` the full 64 B frame is in `~/.cache/beastx-validate/run-output.txt`; the script compared all 64 bytes, not the shortened text.
- Reply handling: our `decodeReplyFrame` skips the CRC for `0xaa`, `0x1a`, `0x35` and checks only the high CRC byte for the rest, matching `0x48480d`..`0x484873`. The driver also re-sends on `rx[3]==0x50` (up to 3, `0x484890`) and re-reads when `rx[3]!=tx[3]` (up to 3, `0x4848e1`); `reply.ts` does neither, so that is for the transport layer (`apps/web/src/device/device.ts`, not reviewed here). inference
- Writes are read-modify-write in both: neither side is byte-correct without a freshly read block.
- Not run: a device read-back; the vendor binary; REA. `bun test` of the package was not run (not needed for this table).
